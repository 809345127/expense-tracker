# 同步服务

一个人、两台手机（iPhone + 安卓）、几千条记录。按这个量级设计的：一个 Go 二进制 + 一个 SQLite 文件，
没有用户系统、没有 ORM、没有缓存。

- `model.go` — 四种记录的形状（这是**协议本身**，两个客户端照它写）
- `store.go` — SQLite 存取 + 冲突解决
- `main.go` — HTTP 接口 + 认证
- `test.sh` — 端到端测试（真起服务、真发 HTTP），跑法 `./test.sh`
- `test_convergence.py` — **两台设备的收敛测试**：用两个模拟客户端照下面那套算法跑真实场景
  （各改同一条、离线各记一笔、删除传播、边推边改、时钟偏差），检查两边最后是不是同一份数据。
  ⚠️ 这个测的是**协议和客户端算法这套设计本身**，不是服务端代码 ——
  两个真客户端都写完才发现设计缺陷，改起来是两边一起改；在这里发现只用改一份文档。
  跑法见文件头。里面第 7 组是**故意用错误实现的控制组**，用来证明第 6 组不是恒通过。
- `deploy.sh` — 交叉编译 + 传到 VPS + systemd，跑法 `./deploy.sh`

## 一、为什么是这个设计

同步这件事只要三个字段就能做对，缺一个都会出问题：

| 字段 | 缺了会怎样 |
|---|---|
| **`id`**（稳定 id，客户端生成） | 用数据库自增主键的话，两台设备各自从 1 开始，一合并必然张冠李戴 |
| **`updated_at`**（毫秒，改动它的客户端写） | 同一条两边都改过时，没法判断该留谁 |
| **`deleted`**（删除墓碑） | 真把行删掉的话，另一台设备下次同步会把它**原样送回来** |

再加一个服务器分配的 **`rev`**（全局递增序号），客户端记住见过的最大值，下次只拉比它大的 —— 增量同步。

### id 怎么取（三种记录三种取法，都是有原因的）

| 记录 | id | 为什么 |
|---|---|---|
| 账目 `expense` | UUID | 没有天然唯一的业务字段 |
| 分类 `category` | **就是分类代号 key** | iOS 侧本来就有这个 key、而且设计上永不改（改名只改显示名）。两台设备各自建同名分类会算出同一个代号 → 自动并成一条；发 UUID 就会变成两条一模一样的分类 |
| 标签 `tag` | UUID | 标签**可以改名**，所以不能用名字当 id（改名会让所有关联失联） |
| 标签关联 `link` | **`<账目id>:<标签id>`** 拼出来 | 确定性。两台设备各自给同一笔账打同一个标签，算出的 id 相同 → 自动并成一条 |

⚠️ **标签有个已知边界**：两台设备**各自独立**新建了同名标签（比如都建了「出差」），会得到两个
不同 UUID 的同名标签。客户端合并时要处理：发现同名（清理后）且 id 不同，保留 id 字典序小的那个、
把关联指过去。分类不会有这个问题（id 就是名字算出来的）。

### 为什么标签关联要当成一条独立记录

「取消一笔账的某个标签」这个动作，**账目那条记录的字段一个都没变**。如果关联只是账目的一个数组、
跟着账目一起传，另一台设备就察觉不到这个变化。所以关联是独立的一行、有自己的删除墓碑。

### 金额是字符串

⚠️⚠️ `amount` 传的是**字符串**（`"24.50"`），不是 JSON number。
iOS 用 `Decimal`、安卓用 `BigDecimal`，中间用字符串，**全程不碰浮点数**。
JSON 的 number 在很多语言里就是 double，`0.1 + 0.2` 那种误差在记账 app 里是不能接受的。

## 二、接口

全部要求 `Authorization: Bearer <token>`（除了 health）。token 只存在 VPS 上的
`/opt/expense-sync/env` 里，**不在这个仓库里**（仓库是公开的）。

### `GET /v1/health`
不要求认证，返回 `ok`。用来确认服务活着。

### `GET /v1/changes?since=<rev>&limit=<n>`
拉取 rev 比 `since` 大的全部记录（**含删除墓碑** —— 客户端要靠它才知道有东西被删了）。
`since=0` 就是全量。

```json
{
  "rev": 42,            // 本页可以安全推进到的游标；客户端下次拿它当 since
  "has_more": false,    // true 就带着新的 rev 再拉一次
  "expenses": [...], "tags": [...], "categories": [...], "links": [...]
}
```

⚠️ **`rev` 不是"库里最大的 rev"，是"本页四张表都已经取干净的那个位置"。**
反例：账目表有 rev 1..500 但被 `limit=200` 截断、只返回到 200，而标签表只有一条 rev=600。
游标要是取全局最大值 600，客户端下次 `since=600`，账目的 201..500 就**永远拉不到了、还没有任何报错**。
（`test.sh` 第 9 组专门测这个；把那段逻辑改成朴素写法，8 笔账当场只剩 2 笔。）

### `POST /v1/changes`
推送本地改动，四种记录混在一个信封里，同一个事务落库、共用一个新 rev。

```json
{"expenses":[...], "tags":[...], "categories":[...], "links":[...]}
→ {"rev": 43, "received": 5, "applied": 5, "stale": []}
```

⚠️⚠️ **`stale` 非空必须给用户看见，不能咽掉。** 它是「被当成旧数据丢掉的那些记录」，
几乎只有一个原因：**这台设备的时钟比另一台慢**。
时钟慢的那台每次推都会被判成旧的 → 它的改动**永久丢失、而且毫无迹象**
（界面上一切正常，只是那笔账在另一台上永远不出现）。
客户端收到非空 `stale` 就该提示「检查两台设备的时间是否一致」。

（注意区分：原样重推同一批数据时 `applied` 也是 0，但那是正常的、`stale` 会是空的
—— 服务端会现查库里那条的 `updated_at` 来分辨这两种情况。）

**冲突规则（客户端必须实现同一条）：`incoming.updated_at > 库里那条` → 覆盖，否则丢弃。**

⚠️ 严格大于、不是 `>=`。这样「把同一批数据再推一遍」是真正的空操作（一条不写、rev 一动不动）。
用 `>=` 的话每次重推都把这些行的 rev 抬高一遍，另一台设备就得重新下载一次没变过的行 ——
客户端 dirty 标记一旦有 bug，两台设备会无限互传，而且看起来一切正常。

⚠️ 时间戳撞在同一毫秒时服务器保留自己那份；推的那一方下次拉取会拿到服务器这份并覆盖本地，
所以最终一致、不会分叉。

### `GET /v1/export`
全量导出（含墓碑）。备份和排障用，正常同步不走这里。

## 三、客户端同步算法（两端一模一样）

```
1. GET /changes?since=<本地记的 lastRev>
2. 逐条合并到本地：
     本地没有这条            → 直接写入
     本地有、且本地没有未推送的改动（dirty=false） → 用服务器这份覆盖
     本地有、且 dirty=true   → 只有 本地.updated_at > 服务器.updated_at 才保留本地，
                               否则用服务器这份覆盖并清掉 dirty
   ⚠️ 写入拉下来的数据时**绝不能顺手把 dirty 置 1**，否则两台设备无限互相推送
3. has_more 为 true 就带新的 rev 回到第 1 步
4. POST /changes，body 是本地所有 dirty=true 的记录
5. 成功之后：清掉这些记录的 dirty，把返回的 rev 存成 lastRev
```

**本地写入的规矩**（两端都要遵守）：

- 任何本地改动 → 设 `updated_at = 现在`、`dirty = true`
- 删除 → `deleted = true` + 上面那两条，**不是把行删掉**
- ⚠️ 所有查询都要带 `deleted == false` 的过滤条件。漏一处，被删的记录就会在那个页面上冒出来
- 先拉后推（顺序反了不影响正确性，但会多产生冲突）

**先拉后推之后会把自己刚推的东西再拉回来一次**（服务器给它分了新 rev）。内容一模一样，无害；
只要第 2 步不把 dirty 置回 1 就不会循环。

## 四、部署

```bash
cd server && ./deploy.sh          # 交叉编译 → scp → systemd → 从外网真请求一次
```

- ⚠️⚠️ **绝对不碰这台 VPS 的 nginx 和 443 端口**：443 是 xray（翻墙）在用，
  而 **nginx:80 是 xray 的回落目标**（xray config 里 `dest: 80`）。动它们有可能把翻墙链路搞挂。
  本服务自己听一个高端口，跟它们完全隔离。
- ⚠️ 重复部署**不会**换掉 token、也不会动数据库（`deploy.sh` 第 2 步只在 `env` 不存在时才生成）。
  换掉 token 的后果是两台手机全部 401，而那个报错长得像"服务挂了"。
- ⚠️ VPS 的 iptables 是**默认 DROP**、只放行了 22/80/443，而且 iptables 规则**重启就丢**。
  所以放行动作绑在了 systemd 的 `ExecStartPre` 上（`deploy.sh` 里那段），跟着服务一起回来。
  - 为什么不用 `netfilter-persistent`：那东西是把**当前所有规则**快照下来开机重放，
    而这台机器上 fail2ban 在动态管自己的链，快照会把它的临时规则一起固化、容易打架。
  - ⚠️ 那条 `ExecStartPre` 要动 iptables，所以 unit 里**不能加 `NoNewPrivileges=true`**
    （加了 iptables 会 Permission denied，而服务照样起得来 → 「服务 active、外网连不上」，
    症状跟防火墙没配一模一样）。改 unit 的加固项时注意这条。
  - ✅ 2026-09-03 验过（没重启 VPS，用等价方式）：手动删掉那条规则 → 外网真的连不上
    → 只重启服务 → 规则自己回来、外网恢复 → 重启两次仍然只有一条规则（`-C` 去重生效）。
- ⚠️ 判「部署成功」要看**从外网真请求一次的响应**，不能看 `systemctl is-active`：
  服务 active 但被防火墙挡在外面时，两者长得一模一样。`deploy.sh` 第 5 步就是干这个的。

排障：

```bash
ssh root@<VPS> 'journalctl -u expense-sync -n 50 --no-pager'
ssh root@<VPS> 'curl -s 127.0.0.1:8787/v1/health'   # 本机通 + 外网不通 = 防火墙
```
